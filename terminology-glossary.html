1. Top-Level Terms

Sits under Workflow, at the same scope as Vantage Point — both are Workflow-internal, unlike Task, which lives at the vault root (see §9).

2. The Five Vantage Points

Five positions the practitioner occupies and revisits over the course of a workflow, each disclosing an aspect of the workflow that no other vantage can. Scoping is always first; Execution is always last. Movement between the three middle Vantage Points is free and expected.

#Vantage PointWhat it uniquely discloses
1Scoping the WorkflowHuman intent and political/ethical/operational constraint. Always entered first.
2Establishing the Data FrameworkOntological fit (or gap) between the ideal and the given. See §3 below for its internal Activity structure.
3Authoring the Analytical SchemaThe tool-agnostic mathematical/logical structure required to answer the question.
4Designing Spatial Results CommunicationLegibility of the result to the Lifeworld it serves. See §5 below.
5Executing the Analytical SchemaThe operational/computational reality of a specific Stack. Always entered last.

Workflow Stewardship — not a sixth Vantage Point (it has no partial view of its own); the continuous documentation practice that records movement between vantages, including every Backward Glance and Epistemic Choice. Visually: not a node, but the annotation layer on the edges connecting the nodes.

Backward Glance — a named move within Stewardship: the audit performed at a transition between Vantage Points, checking whether the vantage just departed adequately resolved what the next one requires. Not confined to the immediately preceding vantage — can cascade as far back as the actually unresolved question originates (e.g., a Schema-stage gap tracing all the way back to Scoping).

Epistemic Choice — the recurring hard decision, surfaced whenever the idealised model cannot be matched to existing/affordable data: compromise the model, or absorb the cost of harvesting new data. Itself a piece of Design Rationale.

3. Vantage Point 2 — Establishing the Data Framework

Now five tightly iterative Activities (revised from four, then five — Recording added; “Phase” retired in favour of “Activity,” see §1), moving from an idealised conception through formalisation and confrontation with observed reality to digital instantiation:

ActivityNameConcept-level termDefinition
OneIdentifying the Universe of Discourse (Boole, 1854)ConceptThe unconstrained, ideal ontology the workflow would require, independent of what exists or can be observed.
TwoAuditing Existing Data (retitled — “Sensoric Manifold” removed from this Activity; see Activity Four)Feature / Feature Class (GIS-technical terms, deliberately introduced here where the semantic and technical layers confront each other)Does the data exist, and how faithfully does it correspond to the ideal ontology? Audit is ontological, not merely one of coverage/resolution — existing (secondary) data carries the categories of whoever collected it; it is already-synthesised, not raw manifold.
ThreeFormalising the Domain of DiscourseCognised Existence (mass noun — denotes a kind, not yet a countable instance; grammatically deliberate)The Universe of Discourse, bounded. Five commitments (see below). Functions as a validation gate the Analytical Schema must pass through. Triggers a mandatory Backward Glance to Activity Two, re-validating candidate data against the now-rigorous criteria.
FourConfronting the Sensoric Manifold (Kant: Mannigfaltigkeit der Anschauung — the raw, unconceptualised given, prior to any synthesis; not hardware sensor data, and not existing/secondary datasets, which are already synthesised)—Always performed, even where the expected outcome is simple confirmation. Two functions: (1) Validation — does the formalised Domain of Discourse survive direct field contact? (2) Collection — where existing data is insufficient, the manifold is what new data is harvested from; a structured Realisation is extracted per the Domain of Discourse’s criteria. Data collection methodology proper deferred to Chapter [X]; this Activity establishes only its epistemic position.
FiveRecording the Domain of DiscourseRealisation (converges here — see below)The digital instantiation of the formalised model: (1) Schema — a spatial table whose geometry type, fields, and field types faithfully carry the Domain of Discourse’s five commitments (Spatial Character, thematic specification, MMU, typing, topology), and whose coordinate reference system is additionally fit for the Analytical Schema’s intended Operators — CRS fitness is Recording’s own distinct concern, not a restatement of Activity Three’s typing (geometry type itself is settled at Activity Three, under Geometric Type; Recording only checks CRS); (2) Population — entering re-evaluated Accept/Transform Realisations from Activity Two, and digitising Collection Realisations from Activity Four, into that same schema. Corrects a stray earlier claim (still to check for remaining instances) that “creating database tables” belongs to Executing the Analytical Schema (Vantage Point 5) — it does not; see the GIS-as-record vs. GIS-as-analysis distinction below.

Activity Three’s five commitments

  1. Spatial Character (name settled — replaces the earlier working label “discrete or continuous”; chosen because it connotes an assigned, decided role — echoing “Cast of Characters” — rather than a discovered, inherent “Nature”) — is the Cognised Existence a bounded, individually identifiable phenomenon (discrete), or a sampled instance of an unbounded continuous field (e.g., a temperature reading)? Settled before anything else because every other commitment depends on the answer: a continuous Cognised Existence has no boundary for thematic specification’s categorical dimension to bound, no MMU to fall below (its analogue is a minimum sampling/interpolation density), and no discrete extent for a topological containment test. Forward-referenced in full to Chapter [X]. (Open item: propagate “Spatial Character” into the actual chapter prose — as of this glossary update, every live use in the manuscript still says “discrete or continuous” without the settled name.)
  2. Thematic specification — an intensional definition (necessary and sufficient conditions) for every Cognised Existence, letting a practitioner decide whether a specific phenomenon in the world is a legitimate instance of that class, given the Spatial Character already settled at (1). Categorical boundary conditions only now — e.g., does a houseboat, permanently moored and used for public events, count as a building? If venue is elsewhere defined as depending on building, the ambiguity propagates. Worked example: houseboat / building / venue (see below).
  3. MMU (Minimum Mapping Unit) / temporal resolution — spatial and temporal resolution below which distinctions are not honoured. Branches on (1): MMU for discrete Cognised Existences; a minimum sampling density for continuous ones. Temporal resolution applies to both alike.
  4. Typing, in two parts — (a) NOIR attribute typing (Nominal/Ordinal/Interval/Ratio — confirm this is the intended acronym, not “NORI”); and (b) Geometric Type — Point/Line/Polygon/Field, an explicit extension this manuscript adds to Stevens (1946) since spatial representation was no part of his problem. States which spatial Operators are legitimate upon a Cognised Existence, exactly as NOIR states which statistical operations are legitimate upon an attribute (e.g., a road typed as Line supports network analysis but not area calculation; typed as Polygon, the reverse). A continuous Cognised Existence is typed as Field automatically, following directly from (1) rather than as a fresh decision here. Geometric Type is an “inadmissible Operator” check, same family as NOIR — distinct from coordinate reference system fitness, which is a “computable but silently wrong” failure and remains Activity Five’s (Recording’s) job, not Activity Three’s.
  5. Topological/spatial-relationship constraints — e.g., roads may not intersect lakes except at bridges; administrative boundaries must not gap or overlap.

Terminology used within thematic specification:

  • Phenomenon / phenomena — the vernacular, Kantian-justified term for “a specific encountered particular” (this houseboat, this temperature reading) — replaces the earlier, imprecise “thing.” Grammar: phenomenon singular, phenomena plural — check consistently.
  • “Class” replaced by “Cognised Existence” throughout this passage — mechanical fix, stray leftover from earlier TBox/ABox discussion.

Worked example — houseboat / building / venue: Running example tying Activities One through Four together. A houseboat’s status as building is contested (does the Domain require fixed connection to land?); if venue depends on building, the ambiguity inherits downward. Open consideration: whether to resurface this same example concretely at Activity Four (field-testing the houseboat at the jetty) to close the loop across all four Activities with one continuous case, rather than fresh examples per Activity.

Real-world case study — GeoDanmark building specification: Danish national building-object specification (§4, Representation) used as an authoritative, real-world instance of thematic specification — independently confirms houseboats as a genuine edge case (explicitly included: “husbåd og lignende”), gives real MMU thresholds (25 m² outside, 10 m² inside an Area Polygon, both municipally overridable — a real Epistemic Choice made in production), and is used pedagogically to show that formal precision at the structural level (thresholds to the m²) often coexists with unexamined vernacular terms at the level of meaning — e.g., “permanent” is never defined, despite doing the key classificatory work, and is complicated by the same spec’s separate provision for buildings under construction. The verbs skønnes (“is assessed/judged”) and the phrase “og lignende” (“and similar”) appear repeatedly, each silently delegating judgement back to the practitioner. Ties directly to Epistemic Choice / Backward Glance: this is exactly the kind of undocumented judgement Stewardship should surface, not let pass silently. (Full Danish text and English translation on file from drafting session — translation includes translator’s notes on “Områdepolygon” and “forefindes… ikke” worth checking against full GeoDanmark documentation before quoting in print.)

Realisation — a specific, located, data-backed instance (count noun: “a Realisation,” “these Realisations”). First meaningful appearance at Activity Two (is this feature a valid Realisation of the Activity One Concept?), carrying forward into Activity Three/Four (does it satisfy the formalised Cognised Existence, including its thematic specification?). Not used in Activity One — nothing exists yet to realise. Existing-data Realisations (Activity Two) and manifold-derived Realisations (Activity Four) are two different provenances of the same concept, and converge at Activity Five: both are entered into the same physical schema, and the finished spatial table should not itself reveal which provenance a given row came from.

GIS as instrument of record vs. instrument of analysis — resolves an apparent conflict between Activity Five and Vantage Point 5 (Executing the Analytical Schema), both of which involve GIS software. Activity Five uses GIS to build and populate a spatial table — an instrument of record, committing nothing about how the data will later be analysed. Vantage Point 5 uses GIS to execute the Analytical Schema’s Operators — an instrument of analysis. “GIS enters the workflow only at Vantage Point 5” (Part 1, §1.2) refers to this second sense specifically, not to any use of GIS software whatsoever; both places in the manuscript now say so explicitly.

4. Vantage Point 3 — Authoring the Analytical Schema

The Schema’s only admissible input is the Recorded Domain of Discourse (Activity Five Realisations) — neither Activity One Concepts nor the raw Activity Four Sensoric Manifold qualify, since neither has been typed/geometried/CRS-fitted yet. This makes Authoring strictly downstream of both of Establishing the Data Framework’s gates (the five commitments, and Recording’s CRS-fitness check).

Analytical Schema as a Directed Acyclic Graph (DAG) — nodes are individual Operators (buffer, intersect, spatial join, reclassify — see §9 for the full Operator/Tool definition); edges are Realisations flowing from one Operator’s output into the next Operator’s input. Directed: data flows one way, Recorded input → final result, never backward into a completed step. Acyclic: no Operator may depend, even indirectly, on its own output — this is what guarantees the Schema terminates as a finite, well-ordered sequence rather than an undefined circular dependency.

Intermediate/derived Realisations — an Operator’s output is not a return to the Domain of Discourse; it is a new Realisation, often of a Cognised Existence the Domain of Discourse never needed to define because it exists only as an artefact internal to the analysis (e.g., a distance-to-nearest-venue value). The Schema must stay as explicit about these intermediate Realisations’ thematic meaning and typing as the Domain of Discourse was about Recorded ones — an Operator three nodes downstream can fail silently on a poorly-typed intermediate output exactly as the first Operator could on poorly-Recorded input.

Tool-agnosticism secured by the DAG framing — the graph specifies which Operator transforms which input into which output, and in what order, but not which software executes it. See §9 for how each Operator individually carries its own tool-agnostic Schema plus one Tool per Stack — the same duality the DAG as a whole has with its Analytical Recipe (§6).

5. Vantage Point 4 — Designing Spatial Results Communication

“Design” — used throughout in the specific sense of suitability (fitness of a representational choice to its data and its audience), not layout or aesthetic composition. Worth one explicit sentence stating this the first time the Vantage Point is introduced.

Two distinct suitability judgements:

  1. What kind of deliverable — governed by MacEachren’s cartography cube (MacEachren and Taylor, 1994, Visualization in Modern Cartography, Pergamon), three axes: public↔private audience, presenting knowns↔revealing unknowns, low↔high interaction.
  2. How the deliverable represents the data — e.g., classification method (equal interval vs. equal count/quantile vs. natural breaks/Jenks), each suitable to different distributions and audiences, none inherently “correct.”

6. Vantage Point 5 — Executing the Analytical Schema

Restates the GIS = Stack convention explicitly at the point it first becomes operationally relevant.

Analytical Schema → Analytical Recipe — the Schema (Vantage Point 3) is tool-agnostic; the Recipe (a Semantic Asset) is the tool-bound, executed translation of it (e.g., a QGIS tool chain or a Python script). The same Schema can yield multiple valid Recipes. Translation is not free — software-specific defaults (interpolation methods, topology tolerances, CRS handling) can reintroduce undocumented decisions, which should be returned to Stewardship as a Design Rationale addendum rather than silently absorbed.

X-Y Problem — the informal term (not “overfitting,” not Dennett’s “competence without comprehension” — both considered and rejected as imprecise fits) for a well-formed-looking request that answers the stated question (X) while the real prior question (Y) goes unasked. Used in the Introduction’s AI-tutor passage: a student may receive a correct procedural answer (e.g., how to buffer) without realising the real prior question was different (e.g., how to reproject first). The comprehension gap sits with the human framing the prompt, not the AI.

7. Semantic Assets (output of the whole Workflow)

  1. Design Rationale — permanent record of every “wicked problem” and how it was resolved. The artifact produced by Stewardship (Stewardship = the ongoing verb; Design Rationale = the resulting noun).
  2. [Formalised] Data Model / Domain of Discourse — the text-indexed bridge between raw data and human intent. (Confirm final preferred term here now that “Domain of Discourse” has superseded “Data Model” as the Activity Three output — check no stray “Data Model” references remain.)
  3. Analytical Recipe — the decoupled, reproducible, tool-bound script (DAG) — see §6.

9. Task, Operator, Tool

Task — a tool-agnostic, reusable unit of work smaller than a Vantage Point/Activity and possibly smaller than a single Analytical Schema node (e.g., georeferencing, creating a table, correcting a hydrologically-sound DTM, print layout design). Lives at the vault root, not under Workflow — deliberately, because the same Task can be invoked from several different Activities (and, in principle, from more than one Vantage Point), so it isn’t owned by any one place in the Workflow. A Task decomposes into:

  1. one or more human decision points — judgement calls that are not themselves mechanically executable (e.g., deciding which points on an image are usable control points; deciding column names and data types for a new table); and
  2. one or more Operators.

Operator — the tool-agnostic, reusable transformation itself (buffer, intersect, reclassify, CREATE TABLE ...). Precedent: Dana Tomlin’s map algebra classifies exactly this kind of thing as operators (local/focal/zonal/global operators) — see the citation checklist, §8. Formally, “operator” is not restricted to an infix symbol between two operands (the everyday arithmetic sense); the broader mathematical sense — a mapping from one space to another, as in a linear operator or differential operator — is unary or n-ary as needed, and is the sense intended here. “Operation,” used earlier this session for this same concept, is retired — Operator now does that job alone.

Like a Task, an Operator has its own tool-agnostic/tool-bound split, one level further down:

  • Operator Schema (tool-agnostic): what the Operator does, independent of any Stack — e.g., what buffering means mathematically.
  • Tool (tool-bound, one per Stack): a specific Stack’s concrete implementation of the Operator — e.g., “the Buffer tool in QGIS’s Processing toolbox,” “the Buffer tool in ArcGIS’s Toolbox” — each exposing its own parameter surface (QGIS and ArcGIS may differ in how end-cap style, join style, or segment count are specified). Deliberately named after the term the software itself already uses (ArcGIS Toolboxes containing Tools; QGIS’s Processing toolbox), so the abstraction maps directly onto vocabulary students already see on screen.

Operators and Tools are many-to-many, and Tools are versioned. (⚠️ Added; confirm wording.) Operators are kept deliberately simple — each does one thing (clip, save, buffer, dissolve) — while a Tool is whatever a Stack happens to bundle into one dialog. One Tool can therefore realise several Operators through its options: QGIS’s Package layers saves many layers with one common clip extent (and can store their symbology with them), so it realises clip and save for a whole set of layers at once; QGIS’s Buffer with Dissolve result and Keep disjoint results separate realises buffer, dissolve and explode in one run. In the other direction, one Operator can need several Tools: the fringe (outer edge) of a buffer is a Buffer followed by a Difference. And the mapping moves between versions of a Stack: Keep disjoint results separate exists in QGIS 4.2 but not in older releases. A Tool note therefore says which Operators it realises, through which options, and from which version — not the other way round.

Operator family — a group of Operators that do the same kind of work, used as the index students search when they meet a new problem: e.g., Overlay (intersection, union, difference, clip), Proximity (buffer, distance surface, nearest feature), Geometry restructuring (dissolve, explode, merge), Zonal (zonal statistics, tabulate area), Surface from samples (interpolation, kernel density). Families are domain-neutral: the same Proximity Operators serve walking distance to a park in urban design and a habitat network in landscape ecology; what differs is the Domain Example that uses them. For the raster Operators, Tomlin’s local, focal, zonal and global classes (see §8) are families in exactly this sense.

A Recipe (§6) is, in these terms, largely a sequence of Tool invocations for one Stack, plus whatever human decision points the Task’s Schema calls for — Recipe is Task-shaped, Tool is Operator-shaped, and they sit at different granularities rather than duplicating each other.

Note on “Schema” overload: the word now does four jobs in this glossary — the Analytical Schema (the whole DAG, §4), Recording’s Schema (the spatial table structure, §3 Activity Five), Task Schema, and Operator Schema. Each is locally clear, but a reader meeting a bare “Schema” without a qualifier may not know which is meant — write “Task Schema” / “Operator Schema” / “the Recording Schema” explicitly rather than relying on context, until this is resolved (if it ever needs to be).

The full chain: Domain Example → Geospatial Workflow → Task → Operator → Tool. (⚠️ Added; confirm wording.) Above the Workflow sits the Domain Example (§1): a worked case that brings in knowledge from outside the strict geospatial domain — urban design, ethnography, hydrology — and so explains why the Workflow is shaped as it is. Read downwards, each level is more tool-bound and more domain-neutral: the Domain Example is specific to a field and a case, the Workflow to a spatial question, the Task and Operator to a kind of work (tool-agnostic), and the Tool and Recipe to one Stack. Read upwards, a Task such as slope and flow direction is reused by several Domain Examples (hydrological modelling, landslide susceptibility, accessibility), linked rather than copied — the same graph principle as below.

Task composition is a graph, not a hierarchy. A larger Task (e.g., building a hydrological model) can be composed of several smaller Tasks and/or Operators (e.g., correct the DTM → flow direction → flow accumulation), but a smaller Task is not “owned” by any one larger Task — the same correct the DTM Task can be referenced from several different larger Tasks (a hydrological model, a viewshed workflow, a landslide-susceptibility workflow) without duplicating its definition. This mirrors the Analytical Schema’s own DAG structure, and mirrors the reuse pattern wanted for the teaching site (one node, linked into multiple context views — see the Canvas/Kumu discussion).

Task write-up template:

  • Task Schema (tool-agnostic): the decision points + the Operators, in the abstract, with no reference to any specific Stack.
  • Task Recipe(s) (tool-bound, one per Stack): “This Task is implemented in QGIS by …”, “in ArcGIS by …”. Multiple valid Recipes can exist per Task Schema, exactly as for the Analytical Schema/Recipe pair at §6.
